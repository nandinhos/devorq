## Sumário Executivo

O DEVORQ v3.8.5 tem uma fundação de engenharia acima da média para bash puro — router limpo (bin/devorq, 190 LOC), escritas atômicas (DQ-004), fail-closed genuíno no check-story do AUTO, audit trail JSONL e backlog DQ-001..030 fechado — mas a promessa central está quebrada exatamente nos pontos de maior valor: 'devorq flow' sai com exit 0 e imprime 'Flow completo!' com gate vermelho, o gate de verificação do AUTO aprova delegates que não produzem nada, e o modo clássico é majoritariamente fail-open (GATE-2 passa sem runner, GATE-3 passa vazio, GATE-4 só conta arquivos). O maior risco operacional é o run overnight do modo AUTO: loop que re-seleciona eternamente a mesma story falha queimando API real, prompts interativos que matam runs headless, árvore contaminada sem rollback, commits cegos a arquivos novos e sub-agente com --dangerously-skip-permissions sem nenhum guardrail duro. A memória — o segundo pilar do pitch — destrói seu próprio conteúdo (sanitize mutila código nas lessons, a sintaxe documentada de capture grava lixo literal) e o handoff descarta os campos que o próximo LLM mais precisa. A maior alavanca de valor é barata: ~80% dos 106 findings são correções de poucas linhas (return 1, TTY guard, jq --arg, flock, git status --porcelain), e o próprio repo já contém as soluções corretas (detecção fail-closed do check-story, spec::validate, lessons::search) que só precisam ser ligadas aos gates que as ignoram. Estrategicamente, o diferencial único e defensável — loop PRD portável entre harnesses + verificação por story + lições persistentes — é onde estão os maiores gaps, enquanto parte relevante da superfície (Context-Mode, handoff manual, code-review próprio) duplica o que Claude Code/Codex/Cursor já fazem nativamente; dois adapters de ~60 LOC transformariam o AUTO de demo interna em produto utilizável por terceiros. Maturidade atual: casca boa, bordas não confiáveis para autonomia sem supervisão — a distância até 'elite' é menos de redesign e mais de fazer o que existe falhar de verdade quando está vermelho.

## Top 10 Críticos (síntese)

1. 'devorq flow' retorna exit 0 e imprime 'Flow completo!' mesmo com gate falhando — a promessa de gates bloqueantes não bloqueia no nível de processo (lib/commands/workflow.sh:167; causa-raiz compartilhada: devorq::error é echo que retorna 0, lib/helpers.sh:97).
2. O gate de verificação do AUTO não verifica a story: check-story.sh só roda a suite pré-existente, então um delegate que não produz nenhum diff é marcado done — comprovado pelo próprio teste E2E (skills/devorq-auto/scripts/check-story.sh:180).
3. GATE-2 é fail-open: runner declarado mas ausente passa em silêncio e stacks Node/Go/Rust nunca são testadas, enquanto o AUTO já tem a detecção fail-closed correta que o clássico ignora (lib/gates.sh:192).
4. A instalação de 1 linha do README baixa só bin/devorq, que exige lib/ inteira — o primeiro contato de qualquer dev novo com o produto é 'No such file or directory' (README.md:35).
5. Sob --all/--force-continue o loop re-seleciona eternamente a mesma story falha sem critério de parada, queimando API overnight (loop-auto.sh:865), sobre árvore contaminada sem rollback que cascateia falhas para todas as stories seguintes (loop-auto.sh:663).
6. Prompts interativos sem guarda de TTY matam (EOF + set -e) ou travam para sempre runs headless no meio do loop autônomo, perdendo failures.md e summary exatamente quando há falha (loop-auto.sh:804/557, lib/visual.sh:218).
7. O commit-por-story é cego a arquivos novos (untracked invisíveis a git diff) e engole falhas com '|| true' — story done sem commit — além de ignorar o guard de segredos DQ-014 antes do git add -A (loop-auto.sh:497/507).
8. Qualquer aspa num bullet do SPEC.md corrompe o prd.json para vazio via concatenação de programa jq — injeção + DoS no insumo de todo o modo AUTO (skills/devorq-auto/scripts/prd-from-spec.sh:108, idêntico em lib/auto.sh:108).
9. A memória destrói seu conteúdo mais valioso: sanitize_input mutila comandos/código nas lessons antes de persistir (lib/lessons/crud.sh:30) e a sintaxe documentada no README grava '--problem' literal como problem (lib/commands/lessons.sh:43).
10. O gating de CI está invertido: só a suite Playwright é required check e gates.spec.ts nunca asserta exit code — uma regressão que inverta a semântica de qualquer gate passa pelo único check bloqueante (e2e-tests/tests/gates.spec.ts:120).

## Findings — Severidade CRÍTICA

### 🔴 Quick Start do README instala uma CLI quebrada (curl baixa só bin/devorq, que exige lib/)

- **Local:** README.md:35 · **Dimensão:** core-cli · **Categoria:** bug · **Modo:** ambos · **Veredito:** CONFIRMED
- **Problema:** O Quick Start manda baixar apenas bin/devorq via curl para ~/bin, mas bin/devorq é 'apenas o ROUTER' e faz source incondicional de lib/helpers.sh, lib/visual.sh, gates, context, lessons e lib/dispatchers/*.sh resolvidos relativos a DEVORQ_ROOT (pai do script). Instalado sozinho, DEVORQ_ROOT vira ~ e o primeiro source falha com erro bruto de bash, sem mensagem acionável. Reproduzi: copiei bin/devorq isolado e rodei `devorq version` → 'line 42: .../lib/helpers.sh: No such file or directory', exit 1. A checagem amigável de diretório ausente só existe para dispatchers (bin/devorq:54-64) e roda DEPOIS dos sources que já quebraram. A porta de entrada do produto não funciona.
- **Evidência:** README.md:35 `curl -fsSL .../main/bin/devorq -o ~/bin/devorq` vs bin/devorq:42 `source "${DEVORQ_LIB}/helpers.sh"`. Teste real: `.../fakehome/bin/devorq: line 42: .../fakehome/lib/helpers.sh: No such file or directory` exit=1. INSTALL.md documenta o fluxo correto (git clone + PATH).
- **Correção:** Trocar o Quick Start pelo fluxo do INSTALL.md (git clone + symlink/PATH). Adicionalmente, em bin/devorq, antes dos sources: `[[ -f "${DEVORQ_LIB}/helpers.sh" ]] || { echo '[ERROR] instalação incompleta — DEVORQ requer o repo completo: git clone https://github.com/nandinhos/devorq' >&2; exit 1; }`.

### 🔴 devorq flow retorna exit 0 e imprime 'Flow completo!' mesmo com gate falhando

- **Local:** lib/commands/workflow.sh:167 · **Dimensão:** gates-workflow · **Categoria:** bug · **Modo:** ambos · **Veredito:** CONFIRMED
- **Problema:** O coração da proposta de valor ('gates bloqueantes') não bloqueia no nível de processo. Quando um gate falha, cmd_flow chama devorq::error (que é apenas 'echo >&2', helpers.sh:97) e faz 'break' — mas após o loop executa devorq::audit_log 'flow' 'end' 'completo' e devorq::success 'Flow completo!', retornando 0. Verificado empiricamente: em projeto vazio, GATE-0.5 imprime FALHOU, seguido de '[OK] Flow completo!' com EXIT_CODE=0. Qualquer agente autônomo, CI ou script que verifique o exit code de 'devorq flow' vê sucesso com gates vermelhos — o gate é informativo, não bloqueante.
- **Evidência:** workflow.sh:167-174: `if ! devorq::cmd_gate "$gate" 2>&1; then devorq::error "Gate ${gate} falhou — parando flow"; break; fi ... devorq::success "Flow completo!"`. Teste real: `devorq flow "teste"` em dir vazio → '[INFO] GATE-0.5: FALHOU ... [ERROR] Gate 0.5 falhou — parando flow ... [OK] Flow completo!' e `echo $?` = 0.
- **Correção:** Trocar break por retorno com falha: `local failed=0; ... { devorq::error ...; failed=1; break; }` e no fim `[ $failed -eq 1 ] && { devorq::audit_log flow end "falhou gate ${gate}"; return 1; }`. Também registrar 'fail' (não 'completo') no audit_log. ~4 linhas.

### 🔴 GATE-2 é fail-open: runner declarado mas ausente passa, e stacks JS/Go/Rust nunca são testadas

- **Local:** lib/gates.sh:192 · **Dimensão:** gates-workflow · **Categoria:** bug · **Modo:** classico · **Veredito:** CONFIRMED
- **Problema:** gate_2 só detecta PHP (composer.json+tests/) e Python (pytest.ini/pyproject.toml). Projeto Node com package.json+vitest/jest, Go, Rust: 'Nenhum framework de teste detectado' → warn → PASS, sem rodar nada. Pior: se pytest.ini existe mas pytest não está instalado, o bloco é silenciosamente pulado e o gate PASSA — verificado empiricamente com suite pytest falhando e pytest ausente → '[PASS] GATE-2: Tests Pass OK'. O modo AUTO já resolveu isso corretamente (check-story.sh DQ-005 é fail-closed com DEVORQ_AUTO_ALLOW_NO_RUNNER=1 e detecta package.json) — o modo clássico ficou para trás.
- **Evidência:** gates.sh:221-228: `if [ -f pytest.ini ]...; then if [ -d tests ] && command -v pytest &>/dev/null; then pytest -q ...` — sem `else` para pytest ausente. gates.sh:192: detecção cobre apenas tests/, phpunit.xml, pytest.ini, pyproject.toml, bin/devorq, Makefile — zero package.json. Teste real: pytest.ini + tests/test_x.py com assert False, pytest não instalado → exit 0, '[PASS] GATE-2'.
- **Correção:** Alinhar gate_2 com check-story.sh (que já tem a lógica certa): fail-closed quando runner declarado mas ausente (`gate::fail 2 "pytest.ini presente mas pytest não instalado"`), e adicionar branch Node (`[ -f package.json ] && jq -e '.scripts.test' → npm test`). Melhor ainda: extrair a detecção de check-story.sh para função compartilhada em lib e usar nos dois modos.

### 🔴 Verification gate não verifica a story: delegate que produz zero mudanças é marcado como done

- **Local:** skills/devorq-auto/scripts/check-story.sh:180 · **Dimensão:** auto-mode · **Categoria:** gap · **Modo:** auto · **Veredito:** CONFIRMED
- **Problema:** check-story.sh apenas roda a suite de testes pré-existente do projeto. Não verifica nenhum acceptance criterion da story, não exige que o diff seja não-vazio, não exige testes novos. Um agente delegado que não faz NADA (ou produz mudança irrelevante) passa no gate — a suite existente continua verde — e a story é marcada passes=true. O próprio teste E2E do adapter prova isso: em DRY-RUN (zero arquivos criados, verificado na linha 118 do teste) a story sai com passes=true/status=done. Para o objetivo de servir devs experientes overnight, esse é o buraco central de confiança: quem valida o que o agente produziu é uma suite que não sabe da story.
- **Evidência:** test-opencode-delegate.sh linhas 93-97 exigem `passes==true` e linha 118 exige `[[ ! -f "$TESTDIR/hello.txt" ]]` no MESMO run — done sem entrega. check-story.sh só roda pint/phpunit/pytest/npm test genéricos; acceptanceCriteria nunca são lidos.
- **Correção:** Guard mínimo no loop após o delegate: `git status --porcelain` vazio → falha da story (delegate no-op), exceto flag explícita por story. Segundo degrau: exigir que o diff toque arquivos de teste quando a story tem criteria testáveis. Terceiro (opcional): passo de auto-avaliação dos acceptanceCriteria pelo próprio delegate antes do verify.

## Findings — Severidade ALTA

### 🟠 uninstall: mensagem 'Preservando .devorq/' é falsa e qualquer tecla confirma rm -rf

- **Local:** lib/commands/utils.sh:64 · **Dim:** core-cli · **Cat:** bug · **Modo:** classico
- **Problema:** Dois problemas de perda de dados no mesmo comando: (1) o prompt diz 'Ctrl+C para cancelar, Enter para confirmar' e faz `read -r` sem inspecionar a resposta — digitar 'n' + Enter também apaga o repo inteiro; (2) o bloco imprime 'Preservando .devorq/ (version, config)...' mas em seguida executa `rm -rf "${DEVORQ_ROOT}"`, que remove .devorq/ junto (é subdiretório de DEVORQ_ROOT). A mensagem promete preservação que não acontece — se o usuário tem lessons/context em .devorq/ do repo DEVORQ, perde tudo.
- **Correção:** Exigir confirmação explícita: `read -r ans; [[ "$ans" == "yes" ]] || { devorq::info 'Cancelado'; return 0; }`. E ou preservar de fato (mover .devorq/ para backup antes do rm) ou apagar a mensagem mentirosa. Guardar também `[[ -t 0 ]]` para nunca apagar em contexto não-interativo.

### 🟠 devorq build aborta no 1º gate falho sem sumário; a 'contagem honesta' é código morto e o exit code do ramo de falha seria 0

- **Local:** lib/commands/utils.sh:108 · **Dim:** core-cli · **Cat:** bug · **Modo:** ambos
- **Problema:** Sob `set -e` (ativo em bin/devorq), `devorq::fail "Gate $gate falhou"` como statement simples retorna 1 e mata o processo no primeiro gate vermelho — o `((failed++))` (que também retornaria 1 com failed=0, outro gatilho de set -e) e todo o bloco '═══ Resultado ═══' com a contagem `$failed de $total` (o fix DQ-028 de 'contagem honesta') nunca executam. E se o loop sobrevivesse, o ramo de falha termina em `devorq::error` (echo, retorna 0) sem `return 1` — build sairia verde com gates vermelhos. O exit 1 atual é acidente do set -e, e o usuário perde o diagnóstico de quais/quantos gates falharam. Reproduzi com script mínimo: imprime '[FAIL] Gate 1 falhou' e morre, exit=1, sem sumário.
- **Correção:** No loop: `if ! devorq::cmd_gate "$gate"; then devorq::warn "Gate $gate falhou"; failed=$((failed+1)); fi` (pré-soma nunca retorna 1) e no final `else devorq::error "..."; return 1; fi`. Um teste unitário que roda cmd_build com um gate forçado a falhar e assere sumário + exit 1.

### 🟠 verify em pipeline não-interativo trava ou morre: fallback manual usa read sem guarda de TTY

- **Local:** lib/visual.sh:218 · **Dim:** core-cli · **Cat:** gap · **Modo:** auto
- **Problema:** devorq::verify::manual faz `read -r confirm` sem checar `[ -t 0 ]`. Em CI ou no modo auto (agente sem stdin interativo): com stdin em EOF, read retorna 1 e set -e mata o processo sem nenhuma mensagem; com stdin aberto (pipe vazio), trava indefinidamente. Como o fallback para manual é o caminho comum (ver finding do mismatch playwright_tests/), um `devorq verify` dentro do loop autônomo pode pendurar a run inteira ou falhar mudo. Para um harness que se propõe a servir agentes autônomos, todo prompt interativo precisa de guarda de TTY com saída acionável.
- **Correção:** No início de verify::manual: `[[ -t 0 ]] || { devorq::error 'verificação manual requer TTY — use --playwright ou exporte DEVORQ_VERIFY_ASSUME_YES=1'; return 1; }`. Mesmo padrão para o read do uninstall.

### 🟠 devorq::error não aborta: guardas de uso deixam comandos rodarem com args inválidos

- **Local:** lib/commands/workflow.sh:148 · **Dim:** gates-workflow · **Cat:** bug · **Modo:** ambos
- **Problema:** devorq::error é apenas `echo >&2` (helpers.sh:97), mas dezenas de callers a usam como die(): `[ -z "$intent" ] && devorq::error "Uso: devorq flow ..."` imprime o erro e SEGUE executando. Verificado: `devorq flow` sem argumento imprime '[ERROR] Uso: devorq flow [--resume] "<intent>"' e roda o flow inteiro com intent vazio, exit 0. Mesmo padrão em foundation.sh:95 (edit sem doc → grep -qw "" casa tudo e prossegue) e vários outros comandos. É a causa-raiz compartilhada do finding 1.
- **Correção:** Correção única no ponto compartilhado: fazer devorq::error retornar 1 (`{ echo ... >&2; return 1; }`) e nos guardas usar `|| return 1`, ou criar `devorq::die() { echo ... >&2; exit 1; }` e trocar os guardas de uso. Auditar callers com `grep -rn 'devorq::error "Uso'` (padrão consistente, troca mecânica).

### 🟠 Intent passado a 'devorq flow' nunca chega aos gates — detecção DDD/grill nunca dispara

- **Local:** lib/commands/workflow.sh:150 · **Dim:** gates-workflow · **Cat:** bug · **Modo:** classico
- **Problema:** cmd_flow recebe o intent mas só o usa em log/audit — não exporta DEVORQ_INTENT nem grava em context.json. gate_0 lê `${DEVORQ_INTENT:-}` e cai para context.json (gates.sh:60-66), que está vazio em projeto recém-inicializado. Resultado: toda a lógica condicionada a keywords do intent (exploração DDD, grill-with-docs) é código morto no caminho principal. Verificado: `devorq flow "modelagem de domínio DDD com entidade"` → 'DDD não detectado — skip'.
- **Correção:** Duas linhas em cmd_flow antes do loop: `export DEVORQ_INTENT="$intent"` e (se ctx_set disponível) `ctx_set intent "$intent" >/dev/null`. Isso também conserta unify::infer_feature e o resumo do gate_3, que leem intent do context.json.

### 🟠 GATE-0.5: validação de acceptance_criteria tem jq com erro de sintaxe — sempre passa

- **Local:** skills/project-foundation/scripts/foundation-validate.sh:177 · **Dim:** gates-workflow · **Cat:** bug · **Modo:** classico
- **Problema:** A expressão jq que conta requisitos sem acceptance_criteria tem parêntese sobrando e não compila (verificado: jq exit 3, 'syntax error'). O `2>/dev/null || echo "0"` engole o erro e devolve 0, então requisitos.json com todos os requisitos sem AC passa o GATE-0.5 — exatamente o critério que o README anuncia ('Requisitos funcionais/não-funcionais' validados). Falso verde silencioso no gate que fundamenta o projeto, invocado por gate_0_5 (gates.sh:147).
- **Correção:** Simplificar para uma expressão que compila: `jq '[.requisitos[] | select((.acceptance_criteria // []) | length == 0)] | length'`. E nunca mascarar erro de compilação do jq com `|| echo 0` — usar `|| echo err` e falhar o check quando o validador quebra (fail-closed).

### 🟠 flow --resume pula gates concluídos em tasks anteriores — gates_completed nunca é resetado

- **Local:** lib/commands/workflow.sh:162 · **Dim:** gates-workflow · **Cat:** bug · **Modo:** classico
- **Problema:** ctx_mark_gate acumula gates em gates_completed com `unique` (context.sh:243) e nenhum código reseta o array quando um novo flow/intent começa (grep no repo: só o template do init o cria vazio). Depois que os gates 1-5 passaram uma vez na vida do projeto, `devorq flow --resume "task completamente nova"` pula spec, tests, context e handoff para sempre — bypass permanente por estado obsoleto. Para agente autônomo retomando sessões, é o caminho natural (--resume) levando a falso verde.
- **Correção:** No cmd_flow SEM --resume, zerar gates_completed no início (`jq '.gates_completed = []'`). Alternativa mais robusta: gravar o intent junto (`gates_completed_for: <hash do intent>`) e invalidar quando o intent muda — 3-4 linhas com jq.

### 🟠 Loop infinito na mesma story sob --all/--force-continue (sem critério de parada por falha)

- **Local:** skills/devorq-auto/scripts/loop-auto.sh:865 · **Dim:** auto-mode · **Cat:** bug · **Modo:** auto
- **Problema:** Quando uma story falha (delegate ou verificação), o loop faz apenas `continue` sem alterar o estado da story no prd.json. Como next_story() sempre seleciona a story incompleta de maior prioridade, a MESMA story falha é re-selecionada na próxima iteração. Com `devorq auto all --force-continue` (iterations=999), uma story persistentemente quebrada é re-delegada ao LLM até 999 vezes — overnight isso queima horas e custo real de API sem nenhum progresso e sem nenhum circuito de parada. Pior: a opção interativa '[2] Pular story e continuar' (linhas 807/879) também não marca nada, então 'pular' devolve a mesma story — a opção é inócua.
- **Correção:** Manter um array `failed_ids` no run e excluí-lo na seleção (jq `--argjson exclude`), ou gravar `status: "failed"` na story ao pular. Adicionar `DEVORQ_AUTO_MAX_STORY_FAILURES` (default 2) que marca a story como failed/skipped e segue. ~15 linhas de bash/jq, sem dependência nova.

### 🟠 Sem rollback: story que falha deixa a árvore suja e contamina todas as stories seguintes

- **Local:** skills/devorq-auto/scripts/loop-auto.sh:663 · **Dim:** auto-mode · **Cat:** gap · **Modo:** auto
- **Problema:** Quando a verificação falha, handle_failure só grava JSONs de contexto (pending/, lessons.json) — as mudanças quebradas do delegate ficam no working tree. A próxima story é implementada EM CIMA do estado quebrado, e como check-story roda a suite inteira, todas as stories subsequentes falham por causa da primeira (cascata). Combinado com o loop infinito do finding 1, um run overnight vira retentativas eternas sobre árvore envenenada. Também não há checagem de árvore limpa no início do run: sujeira pré-existente é varrida para dentro do commit da story via `git add -A` quando DEVORQ_AUTO_COMMIT=1.
- **Correção:** Antes de cada delegate, capturar snapshot (`base=$(git rev-parse HEAD)` + exigir árvore limpa no início do run); em falha de verificação, `git checkout -- . && git clean -fd` de volta ao snapshot (ou git stash) antes da próxima story. Warn/abort se a árvore já estiver suja no start.

### 🟠 DEVORQ_AUTO_COMMIT: cego a arquivos novos e engole falha de commit — story done sem commit

- **Local:** skills/devorq-auto/scripts/loop-auto.sh:497 · **Dim:** auto-mode · **Cat:** bug · **Modo:** auto
- **Problema:** git_commit usa `git diff --cached --quiet && git diff --quiet` para detectar mudanças — untracked files são invisíveis a ambos (confirmado empiricamente: story que só CRIA arquivos novos, ex. uma migration, recebe 'Nenhum change para commitar' e retorna 0). Na sequência, `git commit ... 2>/dev/null || true` engole qualquer falha real (hook commit-msg rejeitando, lock, detached HEAD) e a função retorna 0 → o loop imprime 'Commit por story OK' e chama mark_pass. Resultado: story marcada done com trabalho não-commitado — exatamente o cenário que a flag DEVORQ_AUTO_COMMIT existe para impedir ('ciclo recuperável delegate→verify→commit→done', comentário nas linhas 822-824). Adicionalmente, ensure_branch faz `git checkout -b ... || true` (linha 485): se a criação da branch falha, o run segue silenciosamente na branch atual — potencialmente commitando direto na main.
- **Correção:** Detectar mudanças com `[[ -n $(git status --porcelain) ]]`; remover `|| true` e `2>/dev/null` do commit, verificar rc e tratar falha como falha da story (o caller na linha 823 já tem o branch de erro pronto). ## Cobertura Não Realizada (segundo passe recomendado)

- Performance do próprio orquestrador: custo do bootstrap (source de todas as libs a cada invocação), spawns de jq/python3 em loops e latência percebida por agente — nenhuma dimensão mediu tempo de execução dos comandos.
- Portabilidade real fora de Linux/WSL2: bash 3.2 default do macOS, flock inexistente no macOS (proposto como fix em vários findings), divergências de sed -i/date/mktemp em BSD — os findings tocam o tema mas nenhum teste rodou em macOS/BSD.
- Qualidade dos prompts de delegação: o prompt engineering do opencode-delegate.sh e do template de story nunca foi avaliado com run real de LLM (custo, taxa de acerto, qualidade do código produzido) — só dry-run foi auditado; para um harness de delegação, o prompt é metade do produto.
- Concorrência multi-agente sob stress: a ausência de locking foi apontada estaticamente, mas nenhum teste simulou dois runs/agentes simultâneos para mapear os modos de corrupção reais.
- Supply chain e integridade de atualização: 'devorq upgrade' faz git pull sem verificação de tag/assinatura, o bootstrap instala git hooks no projeto do usuário, e o padrão curl|bash dos docs — superfície não auditada como dimensão própria.
- lib/vps.sh e lib/context7.sh foram auditados apenas no caminho crítico; a interface web dev-memory-laravel do HUB (consumidora dos dados sincronizados) ficou totalmente fora do escopo.
- Interface machine-readable para agentes: nenhum comando tem --json/saída estruturada estável; um review dedicado a 'DEVORQ como API para agentes' (contratos de output, exit codes documentados por comando) não foi feito.
- docs/ e EXTRAS.md não foram auditados linha a linha (só amostrados), e a consistência de idioma pt-BR/inglês nos outputs da CLI não foi avaliada como questão de UX/parseabilidade.
- Governança de release: versionamento semântico, tags, CHANGELOG, política de breaking changes do formato de estado (.devorq/version) — mencionado de raspão no finding de migração, sem análise dedicada.
- Recuperação de desastre da memória: backup/restore das lessons locais e do HUB PostgreSQL, e o que acontece com o estado .devorq/ em corrupção de disco — nenhum finding cobre resiliência de dados além da escrita atômica.

## Resumo por Subsistema

### core-cli

O núcleo de dispatch é o ponto forte: bin/devorq (190 LOC) é um router puro e legível, com resolução portável de symlink (GNU/BSD), set -euo pipefail, exit 1 + mensagem para comando desconhecido, e dispatchers finos que só agrupam sources — nenhum comando cai no lugar errado. As fraquezas concentram-se nas bordas: o caminho de instalação do README (curl single-file) está funcionalmente quebrado porque o binário exige lib/ inteira; o error handling colide com set -e (devorq::fail/((failed++)) matam o build no 1º gate sem sumário, devorq::error retorna 0 e silencia falhas em upgrade/build); e lib/visual.sh — a peça mais importante para o modo auto — tem prompts interativos sem guarda de TTY, critérios de detecção Playwright inconsistentes que degradam o gate para confirmação manual (inclusive no próprio repo), e reinvocação de `devorq` via PATH. Nada disso exige redesign: são correções pontuais de return/guard/mensagem, mais a deleção de helpers mortos, que juntas fechariam a lacuna entre o comportamento atual e o padrão de confiabilidade que um harness para agentes autônomos precisa.

### gates-workflow

O subsistema de gates tem boa arquitetura de superfície — sequência canônica única (DEVORQ_GATE_SEQUENCE, DQ-028), persistência de gates concluídos (DQ-007), audit trail (DQ-018) e um modo AUTO genuinamente fail-closed (check-story.sh, DQ-005) — mas a promessa central de 'gates bloqueantes' está quebrada no ponto mais importante: 'devorq flow' retorna exit 0 e imprime 'Flow completo!' mesmo com gate falhando, e o modo clássico é majoritariamente fail-open (GATE-2 passa com suite quebrada se o runner não está instalado e ignora stacks Node/Go/Rust; GATE-3 auto-cria contexto vazio e passa; GATE-4 só conta arquivos). Há uma classe de bugs de plumbing verificados empiricamente: devorq::error não aborta (comandos rodam após erro de uso), o intent do flow nunca chega aos gates (detecção DDD/grill é código morto no caminho principal), --resume pula gates de tasks antigas para sempre, o jq do GATE-0.5 não compila e sempre aprova requisitos sem ACs, e o UNIFY — única fase que confrontaria ACs com a realidade — marca tudo UNKNOWN por chamar função bash dentro de jq. A boa notícia: o modo AUTO já contém as soluções corretas (detecção multi-stack fail-closed, cd para project_root) e a maior parte das correções é de poucas linhas, unificando o clássico com o que o AUTO já faz. Elevar a ferramenta a 'elite' passa menos por gates novos e mais por fazer os existentes falharem de verdade quando estão vermelhos.

### auto-mode

O modo AUTO tem uma espinha dorsal sólida e bem pensada para bash puro: contrato de delegação agnóstico (DEVORQ_DELEGATE_FN) com fail-closed quando não há agente, verificação fail-closed sem runner de teste, mark_pass endurecido contra corrupção do prd.json (DQ-004), journal por adapter, contexto de falha persistido (pending/, lessons.json, failures.md) e um teste E2E real do adapter opencode. Porém ele ainda não é confiável para rodar overnight sem supervisão: os dois defeitos centrais são o loop que re-seleciona eternamente a mesma story falha sob --all --force-continue (queimando LLM real sem critério de parada) e um verification gate que só roda a suite pré-existente — um delegate que não produz nada é marcado done, como o próprio teste E2E demonstra. Em volta disso há uma coroa de robustez faltante: prompts interativos que matam ou travam runs não-interativos, ausência de rollback da árvore quando a story falha (cascata de contaminação), commit-por-story cego a arquivos novos e que engole falhas, sub-agente com --dangerously-skip-permissions sem nenhum guardrail duro, prd.json sem validação (schema existe mas é decorativo) e nenhum lock contra runs concorrentes. Existe também dívida arquitetural: dois motores duplicados (lib/auto.sh guided vs loop-auto.sh Ralph) com namespaces distintos e comportamentos divergentes — incluindo um --no-verify que burla o próprio hook 'inegociável' do framework. A boa notícia é que quase tudo tem correção pequena e nativa (jq/git/flock/trap, ~10-15 linhas cada): com stop-criteria por story, delegate-diff obrigatório, rollback por snapshot git e guardrails de push/worktree, o subsistema chega perto do padrão 'ferramenta de elite' que o objetivo pede.

### state-lessons-handoff

A memória do DEVORQ tem fundações razoáveis — jq é usado quase sempre (fallbacks sed/grep são raros e marcados), o padrão tmp+mv aparece na maioria das mutações, o sync ganhou robustez real (CSV via COPY, pg_literal, STDIN, exit codes fiéis) e há testes de segurança genuínos em test_sync.py. Porém o subsistema falha hoje justamente na sua promessa central: o handoff descarta success_criteria/stories/git-state e carrega um bug de regex que marca GATE-5 como concluído indevidamente (comprovado no handoff.json em disco); a captura de lessons mutila código com sanitização no lugar errado e a interface documentada no README grava lixo literal ('--problem') na memória; e o GATE-4 nunca conecta as lições ao intent — busca sem relevância, gate que só conta arquivos. Integridade de estado é frágil sob concorrência (zero locking, mktemp em /tmp trocando permissões), o modo AUTO mantém uma memória paralela que nunca alimenta a oficial nem o HUB, e o sync é insert-only com round-trip lossy de validated/approved. Nada disso exige dependências novas: flock, upsert do PostgreSQL, jq e ~100 linhas de correções cirúrgicas resolvem os 15 findings.

### rules-skills

A camada rules/skills tem uma boa espinha dorsal conceitual — fonte canônica em rules/, bootstrap + hook commit-msg real, exports por ferramenta, 9 SKILL.md com frontmatter e trigger keywords razoavelmente claros (scope-guard e grill-with-docs são os melhores prompts do conjunto). Porém a promessa de 'regras ENFORCED' não se sustenta: o único enforcement real é o hook de formato de commit; os validadores de `devorq rules check` são inócuos (bug de subshell + --strict que nunca ativa) e as regras Karpathy são guidance sem verificação. O ciclo de vida das regras está quebrado nas duas pontas — `rules apply` copia a versão local stale em vez da global, bootstrap sobrescreve customizações sem backup, e o próprio repo exibe drift vivo (.devorq/rules em v3.8.3 sem a seção de autorização de commit da v3.8.5). Há contradições diretas entre fontes que um LLM lê literalmente: commit-convention.md com tabelas invertidas vs exemplos, manual-commit.md proibindo o commit-por-story que é a essência do modo AUTO, e a SKILL.md do devorq-auto ensinando delegate_task/execute_code (Hermes) enquanto o runtime usa DEVORQ_DELEGATE_FN. Por fim, o desacoplamento de harness parou nas rules: a camada de skills continua Hermes-cêntrica (skill_view, lista hardcoded fictícia, sem export para .claude/skills/cursor/opencode), e o funil pré-implementação acumula 4 fontes de acceptance criteria com 3 skills competindo pelos mesmos triggers — fricção que pesa justamente no público-alvo do modo AUTO.

### security-bash

A robustez bash do DEVORQ é acima da média para um projeto em shell puro: escritas de estado usam o padrão atômico tmp->valida->mv que preserva o prd.json em falha (DQ-004), lib/vps.sh tem allowlist real de comandos SSH + validação de host/porta, context7 `_load_config` substituiu o antigo source-RCE por whitelist explícita de chaves (F-01), há socket de mux SSH por-usuário e um guard de segredos no commit manual (DQ-014). Os arquivos do caminho crítico que li estão genuinamente defendidos. As fraquezas concentram-se em dois pontos: (1) o parser SPEC->prd (prd-from-spec.sh e lib/auto.sh) constrói programas jq por concatenação de string, o que corrompe o prd.json com qualquer aspa em um bullet comum e abre superfície de injeção jq — o defeito de maior impacto; e (2) o caminho de commit do modo AUTO, que replica funções de commit sem reaproveitar o guard de segredos nem o hook commit-msg. Some-se a isso um crash por `set -u` em `devorq commit` (chave de array associativo sem `:-`), segredo de API gravado sem chmod 600, e testes de segurança que não exercitam nenhuma das vulnerabilidades reais. Nenhum RCE direto por input de usuário foi encontrado, mas o modo AUTO executa código de LLM sem sandbox, o que amplifica a severidade dos itens de commit/parser.

### tests-ci

A rede de segurança do DEVORQ é rápida (unit 6s, security 0.1s, Playwright 29s) e tem núcleos genuinamente bons — os testes de regressão numerados (DQ-004/005/018/030), o verify-dispatch.sh anti-no-op e o test-opencode-delegate.sh que exercita o loop AUTO de verdade — mas a arquitetura de gating está invertida: o único required check do GitHub é a suite Playwright, justamente a que menos verifica (gates.spec.ts nunca asserta exit code), enquanto unit tests e shellcheck não bloqueiam merge. Há teatro de teste mensurável: test_input_sanitize não pode falhar, test_sql_injection testa um regex do próprio teste, test_sync.py testa cópias inline das funções de segurança, e o teste e2e de path traversal nunca usa o payload. A suite E2E não é hermética — herda DEVORQ_* do ambiente, o que hoje produz 71/77 sob ci-test.sh vs 77/77 standalone e chegou a gravar ~40 lessons de teste dentro do .devorq real (trackeado no git, contra o próprio README). O ci-test.sh reporta 'ALL TESTS PASSED' com 6 falhas E2E (não-bloqueante por default) e tem um bug de set -e que aborta o suite na primeira falha real sem sumário. O modo AUTO tem happy-path coberto mas zero testes dos caminhos de falha do loop (retry, fallback, pending/failures), e essa cobertura vive fora do CI. As correções de maior alavancagem são pequenas: exit codes nos specs de gates, env limpo nos helpers E2E, '|| true' nos contadores, e promover CI+lint a required checks.

### elite-strategy

O DEVORQ v3.8.5 tem uma casca de engenharia genuinamente boa — router/dispatchers limpos (bin/devorq com 190 LOC), hardening de entrada auditado, backlog DQ-001..030 fechado com fail-closed no AUTO, gates persistidos com --resume, e CI com E2E como required check. Porém, medido contra o estado da arte de harnesses (Claude Code, Aider, OpenHands, Kiro/spec-kit, ralph-loops), o diferencial estratégico está oco nas pontas: o modo AUTO — a proposta de valor para agentes e devs com specs prontas — não roda end-to-end em nenhum harness mainstream (só opencode/Hermes), não é headless-safe (prompts interativos no meio do loop autônomo), verifica stories com suíte genérica em vez dos acceptance criteria, e consome um prd.json sem schema gerado por parser regex de headings. Na distribuição, o install de 1 linha anunciado está quebrado desde o refactor modular, e a documentação de onboarding se contradiz entre README, SPEC e HANDOFF. Ao mesmo tempo, parte relevante da superfície (Context-Mode, handoff manual, code-review próprio, Context7) duplica o que os harnesses modernos já fazem nativamente, enquanto o trio realmente único — loop PRD portável + verificação por story + lições persistentes — é onde estão os maiores gaps. A boa notícia: quase todas as correções de maior alavanca são pequenas (2 adapters de ~60 LOC, guard de TTY, campo verify por story, install.sh, poda de docs) e transformariam o AUTO de demo interna em produto utilizável por terceiros.
